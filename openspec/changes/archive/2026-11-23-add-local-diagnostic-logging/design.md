## Context

Fiction Writer 是 Windows 优先的 Electron 桌面应用。在 `electron/main.ts` 中，主进程持有窗口和 IPC，并管理 `electron/worker.ts` 所在的 Node 后台进程；React 通过 `electron/preload.cts` 访问有限的应用接口。`electron/journal.ts` 是内存通知缓冲；`electron/agent/runs.ts` 的 Session JSONL 用于恢复会话，不能作为诊断日志。`electron/agent/loop.ts` 只涵盖通用 Pi loop；单章、长篇只读取材和整书阶段分别有独立入口。现有三份主规范的行为不变，本变更新增独立的诊断能力。

## Goals / Non-Goals

**Goals:**

- 两份 UTF-8 日志只存本地，默认开启，同日追加、跨日切换并按 30 个本地自然日维护。
- 记录正常运行的关键动作和实际结果，不只记异常；用两份日志能追查一个 Run、一次工具调用、一次落盘通知或一次阶段恢复。
- 不记录密钥和用户内容；日志系统异常不拖住编辑、模型请求或退出。README 让使用者无需开发工具也能找到文件和编号。

**Non-Goals:**

- 不建日志平台、网络采集端点、常驻服务、交互式日志查看器或指标面板，不要求额外数据库或 SDK。
- 不逐 token 打印、收集完整控制台或提供「包含原始请求」的调试开关；不把诊断日志用于重新运行任务、恢复 Session 或备份作品。
- 不改模型协议、工具执行语义、会话持久化格式、工作流检查点或作品存储策略；日志是对已有行为的观察。

## Decisions

### 1. 主进程统一追加写入，前后端各一份日文件

在主进程建立单个异步文件写入器，在 `app.whenReady` 后、启动 worker 和窗口之前初始化，路径取 `app.getPath('userData')/logs`。默认 Windows 是 `%APPDATA%\fiction-writer\logs`，测试走已隔离的应用数据目录，不能写生产目录。正常启动，backend 文件追加 `app.started`，前端完成初始化后，frontend 文件追加 `ui.ready`；如果前端没起来，在 backend 记录失败，不写虚假的 `ui.ready`。同日重启使用既有文件；每次启动有新 `bootId`，后端重启和前端重载使用新实例标识而非新 `bootId`。

```text
React / preload ── 专用受限 IPC ──┐
                                   ├─ Electron 主进程校验与异步追加
后台 worker ── 独立诊断消息 ──────┤    ├─ frontend-YYYY-MM-DD.jsonl
主进程与进程生命周期 ─────────────┘    └─ backend-YYYY-MM-DD.jsonl
```

用现有 Node 文件能力做串行、可合并的追加，不需要三个进程各自抢写，也不需要另起服务。不同文件始终都是 UTF-8 JSONL，不覆盖或截断已有记录。崩溃留下不完整的尾行时，补行分隔符再追加，不修改旧数据；README 提醒解析时可跳过破损行。

主进程接纳记录时同时决定 UTC 时间戳和本地 `day`；按 `day` 选文件，队列跨午夜不改变已经分配的日期。按本地日历算今天和前 29 天，而不是用 30×24 小时或文件的修改时间。启动时清理，运行中用低频的跨日检测和下一条写入兜底，包括长时间打开或休眠恢复。清理只处理 `logs/` 下匹配两类名称、日期可解析、早于截止日的普通文件，不递归、不跟随链接；其他文件、无效日期和时钟回拨造成的未来日期不会被误删。过期的排队项不得因迟到又创建过期文件。运行中临时清理失败时，同一天最多再尝试两次，每次间隔至少一分钟。应用关闭时不清理，等下次启动。

### 2. 白名单事件与关联上下文，不拦截任意 IPC

共享契约定义 `schemaVersion`、`event`、`level`、`source`、`time`、`day`、`bootId`、`logSeq` 和按事件限定的元数据。`logSeq` 是本次启动的写入接纳顺序，不代表跨进程精确发生顺序；已有 `Journal` 的 `journalSeq` 和 worker 实例标识用于判定通知是否断档。应用版本、构建标识（有则记录）及 worker/renderer 实例在 `*.started` 或 `*.ready` 中可查询，不要求所有事件重复庞大的版本数据。阶段耗时用单调时钟，绝对时间用于跨文件对照。

一次操作以 `requestId` 关联界面、主进程和 worker；在任何可能拒绝请求的验证之前分配，现有数值 IPC ID 只负责传输答复。运行被接纳后把 `requestId` 与现有 `runId` 绑定，同时记录 `workspaceRef` 和 `sessionRef` 等应用生成的技术标识。向 loop、模型、工具、工作流和文件服务传递小型诊断上下文，不维护「当前全局运行」，不同目录可以同时运行。每次模型请求有独立 `spanId` 和 `lane`（`agent` / `draft` / `readback` / `workflow` / `probe`），loop 轮次、工具调用、文件提交各有局部关联标识。模型返回的工具调用 ID 不直接写，使用应用生成的调用序号/ID。工作区提交通知沿用实际 `journalSeq`，以提交标识关联变更；前端回执的 `workerId`、`journalSeq`、`changeId` 和工作区引用须匹配主进程已发布的通知。外部 watcher 触发用独立原因编码，不伪装成受管理提交。

前端通过 preload 的窄接口上报允许的本地事件，主进程验证发送者、消息和限制，按真实通道决定 `source`，不信任消息自报身份。操作的安全请求标识可以由可信 preload/主进程分配，再在 IPC 两侧关联现有结果；不要把设置保存和凭据解密请求的参数透传给日志。worker 使用独立诊断消息，不把诊断送进 `fw:push`，避免增加 UI 通知和形成反馈环路。Harness 运行失败展示可选择复制的 `runId`；发送请求在取得 `runId` 前被拒绝则用 `requestId`，不需要额外日志窗口。

### 3. 正常级别的埋点与最低信息量

以下事件名可微调，开始/结果、因果标识和排障信息不得省略。记录成功、失败、取消、超时、拒绝和部分提交的区别；高频低层通知合并，但真实的轮次、工具、Skill 和提交不做常态抽样。

| 路径与接入点 | 必记信息 |
|---|---|
| `electron/main.ts`、`preload.cts`、renderer 入口 | 启动、窗口/worker 就绪、加载失败、渲染进程退出、后台退出/重启与关闭阶段；允许的操作类型及 IPC 开始、最终结果或超时。前端关键操作以用户动作与落到界面的结果记，不记鼠标移动、每次击键和每轮渲染。主进程能捕捉的崩溃信号独立记入 backend。 |
| `worker.ts`、`RunManager` | 请求拒绝原因、请求到 Run 的绑定、Session 新建/关闭或硬删除、工作区不可用、运行开始/终止、停止请求与实际停止、因程序中断恢复的状态；不把「已请求取消」当成「已停止」。 |
| `loop.ts` 和模型适配器 | 每次 loop 实际轮次开始/结束及继续/终止的理由，模型请求开始、协议／配置引用、有效思考档位、收到 HTTP 状态、首个可用流式事件的耗时（如发生）、收尾或流解析失败；能区别模型拒绝、网络错误、触及轮次上限和用户取消。验证连接的模型调用也用同结构记录。 |
| 工具解析、注册包装器与 Pi 生命周期 | 从模型给出调用候选起记，关联参数校验通过/拒绝、实际开始、结束、耗时和结果是否已送回模型。未知工具或参数无法解析不能仅靠 `tool_execution_start`（它们可能从未执行）；定义名称白名单、统计实例中的合法字段及未知字段数。结果按语义分类：如命令的真实退出码、超时/取消/终止确认和截断标记，文件读写的类型/大小与结果，不保存原文或输出。 |
| `skills.ts` + `worker.ts` 实际路径、`draft.ts`、`chapter-readback.ts`、`workflow.ts` | Skill 读取成功/失败与实际注入某条写作路径分别记录，包含静态 Skill 标识、版本或资源指纹和选用原因；不得声称模型遵循了 Skill 只因载入成功。写章记录原文回读选用、片段命中/缺失及数量、预览开始/结束与提交结果；整书记阶段开始、复用/跳过（例如人工已写章）、完成/失败、检查点写入/验证、恢复或过期的原因与阶段/章引用；不重复输出正文或创作指令。 |
| `workspace.ts`、`Journal`、`src/runtime.ts`、`Workspace.tsx` | 文件操作类型、稳定文档引用、执行前提与观察到的短修订指纹、提交/未提交项数和有限的引用；随后记录通知发出、前端收到的序号、断档的预期/实际序号、补读开始/结束、实际应用的修订指纹、保留草稿或清除预览的决定。只在发 **book change** 及状态边界留痕，不为每个正文增量和普通运行心跳写日志。 |

例如 backend 中先有 `tool.requested → tool.started → workspace.commit → workspace.notified`，前端若漏收可看到 `ui.sequence_gap → ui.reload.started → ui.revision_applied`，通过 `bootId`、worker 实例、通知序号和短修订跨文件对齐。如果只有提交没有通知或收到通知后仍读出旧修订，日志必须能区分这两类问题。

### 4. 数据边界、写入负载及故障降级

优先从白名单结构构造记录，再统一做格式、长度和敏感模式检查，不采用「全量采集后再脱敏」。字段只允许应用生成/认可的标识、枚举、数字、已核对的短指纹或分类后的安全描述。允许错误类别、稳定错误码和有限的模块内位置；不序列化任意 `Error.message`、堆栈、进程输出或 HTTP body。普通目录下若需要识别同一文件，使用不含完整路径的本次启动关联标识；不写作者、作品标题、会话标题、个性化配置名、用户路径、模型原生调用 ID 或未定义的字段名。API Key、headers、配置值、提示和对话、正文、附件、完整工具参数/结果、shell 原文/输出和隐藏推理始终禁止；即使 debug 或异常分支也不能打开原文。这不是 Session 回收站：硬删除不因诊断记录而恢复历史；安全操作元数据按统一期限自然过期。

选择队列和持久文件分离，生产路径只入队、不等待磁盘。初始工程预算建议每条不超过 8 KiB、待写最多 2 MiB 或 1,024 条（先达者为限），一次把同一目标的小批记录顺序追加；事件超长以缩小引用列表和计数为主，不截出半条 JSON。溢出或不可写时优先保留运行终态和错误，显式计数因容量/IO 丢弃的记录，在恢复写入时追加有界摘要。拒写只影响该目标日文件的批次，本轮不重复尝试该目标，其他可写文件继续处理。磁盘满、拒绝访问和清理失败不能阻塞程序，失败回退为节流、无内容的局部诊断或安全状态；不递归调用同一个失败 logger，不无限重试。正常退出在现有 worker 收尾后有短时限地 flush；硬崩溃只保证此前已落盘的部分，不开 Windows 守护进程补写。

## Risks / Trade-offs

- **为排查记录详细参数很容易抄到密钥和稿件** → 只接受按事件白名单的元数据；带合成敏感值的测试覆盖正常、验证失败、模型响应和异常源码分支。
- **跨进程接纳顺序和真实因果不等同** → 用 `requestId`、`runId`、调用序号、提交标识和原 Journal 序号还原，不靠排序时间猜；聚合事件标明次数和作用范围。
- **同日文件可能变大，锁文件或故障期间会漏记** → 不记逐 token 或原始 IPC；以有界异步队列、丢弃摘要和短时关闭保护运行。首版保留每天两份文件，不额外引入按大小分卷；通过测试和实际日志密度评估后续策略。
- **当前测试以成功路径为主** → 增加带可控时钟、合成端点和进程临时根的诊断验收，主动制造漏通知、拒绝工具参数、后台退出和重启恢复。

## Migration Plan

新增独立的 `logs/`；首次运行按实际生产路径创建，不迁移任何历史。回退仅停写，不清理用户数据；既有诊断文件可以手动删除。README 增加路径、日文件保留、Windows 打开方式、故障时按日期和排障编号搜索两个文件的示例；保证任何新增的测试目录、样例日志和配置均不进入 Git，不使用真实密钥测试。

## Open Questions

无阻塞决策。首版不做单文件大小分卷、日志分享包和动态级别设置；若实际文件负载显示这层不足，另开变更。
