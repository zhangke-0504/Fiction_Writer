## Context

`Settings.tsx` 目前用一个表单新建和编辑配置；主进程保护 API Key，worker 的 `ProfileStore` 将配置原子保存到应用级 `profiles.json`。`checkProvider()` 测的是流式文本和工具往返，不发现模型能力。`context-budget.ts` 默认按 `64_000 - output - 1_200` 计算输入，`provider.ts` 则为部分官方 DeepSeek Messages 配置硬编码 `16_384`。该值还被用于识别部分直出请求及超时档位，不能只替换常量。

## Goals / Non-Goals

**Goals:**

- 在原设置内增加「选择供应商 → 共用配置表单」，让后续厂商可通过目录条目与独立的能力适配器接入。
- 「保存」一次完成能力查询与全局配置持久化；无查询能力或查询失败也能保存，额度来源可见；既有配置、各小说和重启后的行为可核对。
- 所有实际模型请求共用预算规划，按端点能力、请求用途和拟发送输入留量，长写作请求不再受已知 DeepSeek 的 16,384 固定值限制。已取得供应商额度的配置按本次输入预算动态分配同一会话旧对话的原文空间。

**Non-Goals:**

- 不做 OAuth、CC Switch 的其他厂商分类或搜索、远程模型选号、代理、跨应用供应商同步、额度手工编辑或用量展示。
- 不修整书 Skill 首次请求的选档时点，不改变业务回执、写入、思考设置映射、200 轮上限和输出触限/坏 JSON/断流的既有处理策略。

## Decisions

### 1. 厂商身份、协议、配置实例分别建模

「新建配置」打开厂商选择页：「模型厂商」只有 DeepSeek 一张卡，另放「自定义配置」。选 DeepSeek 时预填名称、官方 Messages 基地址 `https://api.deepseek.com/anthropic` 和协议，模型 ID 仍手输；保持表单可编辑，选择和返回不发请求。选自定义使用现有空白表单与原协议默认。已保存条目继续直接打开编辑，不要求重新选厂商；同一厂商可以有多条具名配置。

后端以稳定 `providerId` 标识目录项，以 `protocol` 决定写作请求的适配和序列化，以原配置 `id` 决定实例。选择 DeepSeek 标签本身不授予发送密钥的权限。以有限目录和可单测的服务端适配器取代按模型字符串四处判断；添加下一家厂商只新增预设、匹配和查询/兜底规则，不重写预算公式或增设一套表单。

### 2. 保存负责查额度，全局配置是唯一持久来源

- 校验配置并保持原加密流程；在 worker 用本次保存后的有效凭据（表单留空时读已加密的 Key）查询。新选中的官方查询来源与旧配置凭据来源不同源时，要求重新明确提供 Key，不能在按下保存时自动把旧 Key 转给新来源。解密、加密或持久化失败不报告成功，也不破坏前一份配置。
- DeepSeek 适配器严格匹配规范化后的官方 HTTPS 写作基地址、标准端口与协议允许路径（官方 OpenAI 格式用于 Chat/Responses；官方 Anthropic 格式用于 Messages；仅保留已支持且经验证的 `/v1` 兼容路径）。使用固定 `https://api.deepseek.com/models` 和该接口规定的鉴权；不能把 `/models` 直接拼在 Messages 基地址后，不跟随重定向。自定义配置、中转站和不匹配的端点不做查询。网络使用短超时、单次尝试和有界响应；不发生成请求、不读小说内容。
- 用精确模型 ID 查唯一条目；只支持官方文档明确列出的兼容 ID 映射。校验 `context_window`、`max_output_tokens` 为正的安全整数且逻辑一致，统一为 `contextWindow`、`maxOutputTokens`；未来支持的厂商若另有独立输入上限或协议/模式输出上限，归一化后作为额外约束。DeepSeek 的 `api_capabilities.anthropic_messages` 声明的是协议行为（如 system 更新方式），不把可省略的字段当成协议探测成功，也不修改现有协议行为。
- 将额度、来源（`provider` / `provider-fallback` / `generic-fallback`）和有限的降级原因随本次配置一并原子持久化，不把失败响应原文写入配置。网络错误、鉴权失败、超时、缺模型或额度不合法都属于「能力未识别」，都按下表继续保存；这不等于验证写作 API 可用。只更新本条配置；打开应用、建书、发请求不刷新，不取上一个端点或模型的额度。保存时禁重复提交，成功后展示额度与来源，保留原有独立的「测试连接与工具」，不增加额度检测按钮。

| 查询未成功时 | 上下文窗口 | 单次输出上限 | 边界 |
|---|---:|---:|---|
| 已知官方 DeepSeek 模型 | 1,048,576 | 393,216 | `deepseek-flash`、`deepseek-v4-pro`，以及官方确认仍映射到 Flash 的 `deepseek-v4-flash` / `deepseek-v4-flash-vision-exp`。仅用于匹配的官方端点和协议。 |
| 未识别的官方模型、自定义或其他未适配配置 | 64,000 | 8,192 | Writer 保守估算，不宣称为供应商的真实能力；不套用 DeepSeek 的数字。 |

额度来源为 DeepSeek 官方文档（2026-11-25 核对）：[模型列表](https://api-docs.deepseek.com/zh-cn/api/list-models/)、[模型与定价及旧 ID 映射](https://api-docs.deepseek.com/quick_start/pricing/)、[Messages `max_tokens`](https://api-docs.deepseek.com/api/create-message/)。Messages 的 `max_tokens` 包含思考 token，模型/思考模式/推理强度可能使有效上限不同。保存的是官方声明的上限或明确标记的估算，不是每种模式下的实测保证。

### 3. 预算按请求用途计算，不把 384 Ki tokens 填进每一轮

保留现有调用方决定何时选普通档、写作大预算档的边界。初始策略值：普通主 Agent 或原默认请求 `8,192`；原先有资格用大预算的整书 Agent、目标章正文、资产生成/同步等请求改用 `65,536`（64 Ki tokens）作为 Writer 的目标；现有探测、摘要和补读等 `1,024` 或 `2,048` 的显式小请求保留原目标。该目标与供应商上限是两回事。已有已确认跨章编辑、定向增补或其他没有选大预算的调用，不为本 change 增加隐式提档规则。

```text
C = 配置的上下文窗口；S = 1,200（本版预留量）
O = min(本次用途目标, 配置的最大输出, 已知且适用的协议/模式上限)
I = min(C - O - S, 已知且适用的独立输入上限)
```

- 同一 `O` 和 `I` 用于装配/裁配与发送：主循环和会话历史保留、正文章节取材、资产/同步、补读、摘要、连接探测均不得一处按默认值裁剪、另一处用不同的出站值。按实际 `system`、历史（含原生工具往返）和工具描述估算输入，沿用必要/可选优先级。在发送前复核最终输入估算；同一请求若限于剩余上下文，实际输出至多为 `min(O, C - 最终输入估算 - S)`，独立输入限额仍生效。最后一层复核不静默改写已经定稿的 `O`；若最终投影违反约束，或必要输入无法在选定预算下装入，沿现有 `context_limit` 停止，不制造空/负额度，不静默丢弃必要内容或引入新重取路径。
- 供应商适配器将规划出的同一数值按协议序列化；不借助对 `extendedOutputTokens` 的真假来选择 DeepSeek 关闭思考或直出能力，也不要求与一个魔术数相等才延长超时。把原先的直出资格（官方兼容端点、符合条件的正文或单结果工具）和长请求超时策略分开表达，保留其适用边界；不因仅有高额度或中转地址而改变思考行为。
- 不提前设置 `wholeSkill`、不搬动 `skill.applied`，也不提前读取待派发 Skill 来提档。本 change 后，已进入大预算档的请求用新数值；第一条携带 Skill 的时序问题仍需后续 change 验证和修复。

同一组 DeepSeek 声明能力下，下表是 Writer 估算用的输入预算，不是模型精确 tokenizer 统计：

| 本次预留输出 | 输入预算（扣除 1,200）|
|---:|---:|
| 8,192（普通） | 1,039,184 |
| 65,536（写作大预算目标） | 981,840 |
| 393,216（供应商最大值的边界示例，并非默认档） | 654,160 |

### 4. 动态分配同会话旧对话的原文额度

这只是总输入预算内部给**同一 Session 的近期旧对话原文**的一份分配，不是新的上下文上限。每次新 Run 开始准备历史时，用主 Agent 首次请求规划的 `I`；`spare` 是扣除系统指令、当前作者消息和工具定义的输入估算后的剩余空间。沿用相同的输入估算，不向供应商重新查询，不按整书提档改动历史加载时点。

```text
空间约束 = floor(max(0, spare) × 43%)
原文额度上限 = floor(I × 5%)        （保存的能力来源为 provider）
原文额度上限 = 9,800                （provider-fallback、generic-fallback 或无已确认额度）
实际原文预算 = min(空间约束, 原文额度上限)
```

`5%` 是 Writer 的历史分配策略，不是供应商的限制。已查得上述 DeepSeek 能力且无更小输入上限时，普通首轮的 `I = 1,039,184`；剩余空间充足时原文预算为 `51,959` 个**估算** token，空间不足时由 `43%` 的约束先降低。即使内置 DeepSeek 兜底也是 1M 窗口，原文上限仍按 `9,800` 处理；它不是保证保留这么多的下限。保留从最近开始装入的完整对话分组，不填满未使用的预算。

超出原文预算的未压缩前缀仍按现有机制生成私有摘要或摘录检查点。已有检查点继续使用，游标不回退；不会为了填满新额度而自动重读检查点之前的原文，原始记录仍可在会话中查看。摘要请求、检查点体积、当前运行内工具往返裁剪、跨会话边界、作品记忆与诊断事件内容均不变。

### 5. 诊断写实际发送，不记录内容

用既有 Run / `spanId` / lane 关联输出目的、额度来源、窗口、供应商声明的输出上限或兜底值、实际出站输出值和最终输入估算；派发记录只在最终请求体交给传输层后发出。能力查询结果与生成成功分开；可以用有限结果枚举记查询降级，但不记录 Key、URL、供应商响应体、请求体、思考内容或文稿。保留已有诊断白名单和安全边界。

## Risks / Trade-offs

- [声明上限不等于某次实际可生成的长度] → 不声称 384 Ki tokens 在所有协议/模式可用；记录策略选择和确实出站值，不把 `output_limit` 当成已修。
- [更多历史可能增大序列化开销、延迟和费用] → 按 5% 与剩余空间约束限制旧对话原文；更大的额度是上限，不主动读更多章节或塞满时间线。小窗口查实后其比例配额可能低于旧规则，此时仍通过摘要或摘录保留必要线索。保留既有取材、文种估算与超时策略，验证必要输入与大输入边界。
- [普通保存引入联网与凭据边界] → 短超时、固定目标、不重定向、失败可保存且明确降级；站点来自后端规则而非表单拼接。未配置或不匹配的站点不发流量。

## Migration Plan

- 旧 profile 缺少新字段仍可读；只对可严格识别的旧官方 DeepSeek 端点/协议赋默认厂商，其他归自定义。无需重新录 Key、换 `id` 或改小说/会话引用；未重新保存前使用适用的本地兜底。启动不迁移联网，也不强制重写文件；下一次主动保存时补齐字段并按新流程发现能力。
- 每次运行继续使用其启动时解析的 profile；编辑后的参数用于后续运行，不改变正在执行的请求。回退版本忽略新增字段，仍使用原配置、加密密钥及原预算；保留配置文件兼容性，不做不可逆存储迁移。

## Open Questions

无阻塞问题。后续 change 再通过实际写作评估 64 Ki 输出目标、首次 Skill 请求提档和触限恢复，不在本变更用无意义长生成探测上限。
