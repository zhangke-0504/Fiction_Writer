## Context

`add-provider-aware-model-budgets` 已将 `standard` 和 `long-writing` 的用途目标定为 8,192 和 65,536，并按全局配置能力约束实际输出和输入。`loop.ts` 在 `ActiveContext.fit()` 前按当前用途选档，`skills.ts` / `NovelTools.skillApplied()` 则等 `onResultSent` 才设置业务标记 `wholeSkill`。因此第一次实际派发整书指南还没提档；当前测试也刻意验证了旧顺序。模型请求之后仍由现有工具完成整书和章节写作，不存在另一条整书流水线。

本地问题记录中的《蝙蝠侠》与「海贼王设定书确认跨章修改」都发生在 Messages 主 Agent。前者有预算时序问题，后者不依赖整书 Skill。旧日志证明响应触限和本轮没有工具执行，不证明是哪类内容耗尽输出；《蝙蝠侠》重测的参数坏 JSON 不属于本类。现有适配器已在 `message_stop` 加 `stop_reason=max_tokens` 时拒绝响应；另有同名 `output_limit` 表示局部增补超过 Writer 的篇幅保护，两者来源必须分开。

开源参考：本地 `design/20261125/openclaw`（`b0454c7`）的 `docs/concepts/model-failover.md`、`src/agents/embedded-agent-runner/run/session-prompt-state.ts` 区分受限续接和原样重发；Pi（`c11a73b`）拒绝被截断响应内的工具调用；Codex（`87de5e9`）的 `codex-rs/core/src/responses_retry.rs` 区分明确的未完成响应和传输重试。Writer 不复制第三方实现，不借这些项目推断 DeepSeek 的实际停止原因或用量。

## Goals / Non-Goals

**Goals:**

- 让首次实际携带合格整书指南的请求选对预算，保持业务授权的派发语义和共同预算规划器。
- 对确认可缩小的 Messages 小说主 Agent 工作，从最后有效状态续接一次；续接后继续逐项完成原目标，重复触限时能安全停下。
- 用独立的夹具和脱敏日志验证两个故障的修复，不把一次恰巧未触限的实盘当成恢复路径验收。

**Non-Goals:**

- 不增加固定整书阶段、作者模式选项、输出提额阶梯、自动模型切换、自动重启 Run 或通用工作流拆解器。
- 不改供应商配置、上下文窗口规则、会话历史比例、读写权限、数据格式或 200 逻辑轮上限。不改变 Chat Completions、Responses、纯讨论、普通目录、子请求（如 `draft`、`asset`、`readback`）和局部增补篇幅保护的失败处理。
- 不保证一次写完任意大纲或任意长正文，不额外实现大纲或写章工具的分段写入接口。

## Decisions

### 1. 预算预判与派发后生效分开

- 在活动 Run 的请求投影处对照可信的 `skill_load` 已执行且成功的结果、匹配工具调用 ID、真实 `generate-novel` 指引和现有整书资格（沿用 `skillApplied()` 的直接写作条件，排除确认编辑和特殊增补入口）。不要从作者措辞、模型自述、`skill_search` 候选或其他工具正文猜测，也不把整书专用逻辑散落进通用供应商适配器。
- 对即将派发的首次成功结果先选 `long-writing`，同一个 `planModelBudget` 负责按配置约束输出并得到输入空间；裁配时保护这条匹配的调用和完整结果，验证最终请求确实含该结果。优先裁减可选上下文；所需结果仍无法随合适预算完整发送就留在原有 `context_limit` 路径，不发一个残缺或普通档的首次整书请求。已生效的整书 Run 继续按该用途规划；通用兜底或较小供应商额度按既有限额夹紧，不硬写 65,536 到请求体。
- `wholeSkill`、目标登记／核对、`skill.applied` 和对应 `tool.result_sent` 仍由真实派发触发，只记一次；计划、预算估算、取消、未派发不得产生这些业务效果。重送同一逻辑轮已合法装配的请求，不能重放 Skill/工具结果的业务回执。不要简单提前调用 `skillApplied()`，也不要先按普通档裁配再只改出站 token。

### 2. 只在明确触限且下一步可缩小时发起一次续接

- 给 Messages 明确终止的供应商长度错误一个可信的类型/来源（保持现有公开分类 `output_limit`）；只在外层小说主 Agent 的批次进入工具执行前消费。断流、坏 JSON、鉴权、上下文不足、子工具的触限结果和 Writer 篇幅保护不属于该触发器。即使触限响应里已有看似闭合的工具块，也拒绝整批；清空这次尝试的临时显示，不把其文字、原生块、参数或伪造回执送回供应商或写入会话。此前有效的调用／结果配对、成功回执和持久成果照常保留。
- 在同一 Run、同一逻辑轮，从失败尝试之前的有效投影重新构建请求，附一条不持久化的内部续接指引：先前触限批次未执行，现有范围不变，只提交一个已核对的小动作，不复述稿件、不重复已完成目标。输入重新通过同一预算规划；续接使用原轮的用途与有效额度，不靠提高 `max_tokens`、改思考等级或降级模型制造进展。整书首次派发的有效 Skill 结果、工具 ID 配对和必要作者限制仍须保留；加入指引后必要输入仍放不下，不派发，外层仍报告触限未恢复并注明原因。
- **整个 Run 最多一次输出触限续接；同一逻辑轮至多一次额外派发，坏 JSON 与触限共享这个轮级上限。** 坏 JSON 后触限、触限续接后坏 JSON 都不会再发第三次；下一正常轮仍按原坏 JSON 规则处理，但整个 Run 的触限续接配额不重置。每个实际请求用新 span，关联原失败 span；逻辑轮和 Run 不因此重启。取消在评估、构建、派发和执行边界均有效。

### 3. 缩小的是当次动作，不是目标或写入校验

首版仅在已派发整书 Skill 的直接整书任务（含已送达 Skill、尚未登记整书目标时的安全起步）和同会话明确确认且仍可承接的跨章编辑中启用。以 `NovelTools` 的有效整书目标、确认方案、实际保存回执、当前现稿修订和待同步事项为准，不从截断响应推断下一章或授权。若没有安全候选、已发生权限／版本冲突或剩余动作不可拆，则不自动派发。

| 已验证的状态 | 可缩小的下一步示例 |
|---|---|
| 指南已送达但目标未登记 | 一次定向 `book_get_context` 核对缺失的基础信息，或用现有工具登记完整有序目标。登记是一个元数据动作，不把十章目标拆成十份；不能从截断文本猜 ID。 |
| 整书已有目标 | 补一项当前缺失的主体／伏笔，写下一个符合整书顺序的空白章，或提交一项合法、独立、简短的大纲或目录变更。若仍需一次生成过长且不可拆的整份大纲，停止并指出该阻塞。 |
| 已确认跨章编辑 | 先核对某一待做目标所需的现稿证据，或执行一个未完成的资产、同章锚点增补或同步目标；保留已确认方案的全部范围和后续待办。 |

- 续接进入「逐项」约束，持续到本 Run 结束；每个模型响应最多给一个经现有工具可独立校验的动作。保留原工具 schema 与执行器，在执行整个候选批次前根据有界候选校验工具、目标、动作、批量基数和请求形状：如 `targets` / 独立 `operations` 至多一项、写章只用简短安排和必要锚点，不在参数里填正文或重贴资料。会话未开始写入前完整登记目标的 ID 列表是元数据而非批量写入。用现有 token 估算器核对单个调用的序列化参数不超过当次有效输出额度的 `1/8`（向下取整）；这是逐项模式的参数体积约束，不是再下调模型的 `max_tokens`，也不能通过截断参数来满足；需要维持原子性的组合（如同一章插入及其已授权大纲补记）仍是一项，不能拆开提交。具体章节／文档修订、锚点、引用、权限和写入约束仍由既有执行边界检查。
- 单步成功可以是新提交、确已完成的目标登记、或为该目标取得先前缺失的必要证据（完成核对用于终结）；未实际写入的目标不得记作完成。重复同一已确认完成/无变化的读取、声明进度、无工具空回复、不合规的多动作批次、或与原范围/稿件冲突，不能算进展或开启新触限续接。允许只在既有最终核对确认全部要求已完成后正常总结；否则第二次触限或不能推进就停止，清楚区分「已保存」和「仍未做」，不知道具体章时不猜。终止后的手动续接沿用现有同会话授权和核对路径，不额外开启自动后台工作。

### 4. 分别验证预算和恢复路径

- 使用已存在的 `model.budget_dispatched` 和 `skill.applied` 对照首次派发，用有限枚举区分「本次首次携带指南」与「整书已生效」等选档依据；不与 `capabilitySource` 混淆。只有实际派发才记录预算，不能提前记 Skill 已派发。
- 用脱敏事件关联原 span、续接 span（实际派发才出现）、轮次、触发来源、执行决定和终态；输出恢复、坏 JSON、无法拆小、无进展、再次触限和取消可区分。只有真实工具回执／写入证明进度，不采集截断参数、原始文本或思考。若供应商没有提供可用用量，不推断哪个部分耗尽额度；本 change 不新增 token 计量功能。
- 先用本地 Messages 夹具验证《蝙蝠侠》式首次派发是否提档，以及海贼王式已确认修改在首次触限、成功逐项推进或第二次触限时的行为；两项都核对出站体、日志和磁盘提交。若另做实际供应商验收，须经授权、用隐藏 Electron 与隔离书库，分别记录首次选档、是否真的触限和各项落盘。未发生触限的实盘不能证明恢复路径，也不误把坏 JSON 计入输出触限。

## Risks / Trade-offs

- [裁配与派发判断不一致] → 以最终可发送投影核对完整 Skill 与工具身份，执行前再验证。
- [缩小动作导致多几个正常往返] → 只在明确触限的恢复执行中进入单步约束；以有用的新证据和真实提交判断是否能继续，仍受原 200 轮约束。
- [模型声称完成或利用单步弄丢安全依赖] → 只接收可以独立提交且满足既有授权／校验的动作；不拆原子提交，余项由现稿核对而不是模型声明。

## Migration Plan

不迁移任何 profile、书稿、会话或工具回执。先落实首次正确选档与独立验证，再挂接触限续接与诊断；已有任务继续通过原来的同会话入口恢复。同步主规范时，新的首派发场景替换原过渡场景 `Use the new budget without claiming the two follow-up fixes`，两者不并存。

## Open Questions

本变更不承诺解决不可拆、必须长输出的单个工具操作。若隔离实测集中出现同一阻塞，后续以实际证据评估该工具的分段或结构调整，不作为本 change 的前置条件。
