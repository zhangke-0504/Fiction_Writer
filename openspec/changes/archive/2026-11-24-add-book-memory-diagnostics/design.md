## Context

`context.checkpoint`、`context.compacted` 和 `tool.*` 已记录会话压缩和工具生命周期，但自动召回直接调用 `recallBookMemory`，不经过工具调度：`worker.ts` 为 Agent 准备提示，`draft.ts` 为单章正文准备独立请求，二者都可能命中。`WorkspaceService.updateBookMemory` 在尽力写缓存时吞掉失败，召回仍能根据现稿运行。仅看 `model.started`、工具成功和稿件提交，都不能区分召回结果或证明某个实际请求携带了记忆。

## Goals / Non-Goals

**目标：** 用一个 Run 内可关联的日志，回答「哪次召回命中」「索引是否真的落盘」「哪个请求携带了哪类证据、来自哪些版本」。可区别同 Run 多章、重试及并发作品，不需访问稿件或 Session 原文。

**非目标：** 不改变召回排序、写章、记忆索引和会话压缩行为；不新增 Harness 界面、日志文件或遥测；不尝试判断模型是否采信证据或生成是否因此更好。

## Decisions

### 1. 观察一次召回，不从模型输出推断

在 `recallBookMemory` 的公共入口分配随机 `recallId`。通过独立的内部诊断观察值传递关联 ID、计数和有限来源元数据，不改变 `BookRecall` / `book_memory_recall` 的返回值或将元数据拼进提示。事件沿用上层 `runId`、`workspaceRef`；显式工具沿用 `callId`，来源枚举区分 `agent`、`draft`、`tool`。相比仅在调用方各打一次日志，共用入口能让三种来源的计数一致，并正确记录异常和取消。

| 事件 | 记录点与字段 |
|---|---|
| `memory.recall.finished` | 召回算完或明确失败、取消。含来源、耗时、状态；成功时分别计 `earlierStory`、`plans`、`reference`、约定条数。成功全零是空结果；只有约定时不记为正文证据命中。 |
| `memory.index.finished` | 进入索引缓存处理后，记录 `unchanged`、`created`、`updated`、`degraded` 或取消；已观测时附复用、重建、失效来源数量。读取出错、内容无效和写入失败用不同白名单分类。 |
| `memory.context.dispatched` | 非空自动召回数据随实际 Agent 或正文请求交给传输层。带 `recallId`、本次 `spanId`、来源类别计数、唯一来源数和省略数；写章沿用目标章引用。 |
| `memory.context.source` | 同一派发下，每个实际携带的唯一来源（文档及版本）最多一条，每请求最多 8 条。记录正文／计划／参考类别、文档类型、指纹、可用时的来源章序。不记录约定文本或单条约定 ID。 |

### 2. 在侧车真实 I/O 上判断索引状态

让工作区侧车操作向召回调用方报告可观察的状态，不靠文件 mtime、watcher 或再次读盘来猜测。缺文件是正常冷启动；只在原子替换成功后记 `created`/`updated`，未替换归 `unchanged`。无效内容或读写失败后仍按现稿走原有内存路径，标为 `degraded`，不重复尝试或清空侧车中已持久化的作者约定。编辑／删除导致的无效版本与达到缓存上限不落盘是不同情况；只统计真正观测到的失效来源。显式写约定的失败仍按原有工具错误返回，不降级成假成功。

### 3. 在派发边界报告实际带出的记忆

在组装 Agent 系统提示和写章上下文时，同时保留与实际附加内容对应的只读诊断描述。Agent 经过 `ActiveContext.fit` 后，只在现有 `provider.turn` 的 `onDispatch` 中记录；写章只在正文 `generate` 的对应 hook 中记录，不从只读补读请求或压缩摘要请求发出。每次真正交给传输层都使用该次请求的 `spanId`；一个 recall 可以对应多轮或重试的多个 span。空记忆、预算失败、取消或冲突导致未交给传输层的请求，不虚报携带记录。显式回忆工具用 `memory.recall.finished` 和现有 `tool.*` 关联，不把工具成功或通用结果回传冒充自动注入。

### 4. 沿用白名单和有界日志

新增 worker 专用事件，标识只允许受控 UUID；字段只由代码构造。文档引用和修订值通过现有日志端的启动期指纹处理，与现有写入事件按同一 `bootId` 和 `workspaceRef` 对照；派发汇总的目标章和来源明细按同一 `runId` + `spanId` 区分。日志不接收 `BookRecall`、缓存对象、原始路径或异常对象。只记录汇总及有上限的明细，不逐片段记录，也不新增磁盘同步等待。否则「能看到原文」虽然易排查，但会破坏现有日志的内容隔离。

## Risks / Trade-offs

- **命中不代表交付或采信** → 分开记录索引、召回、请求派发；是否收到 HTTP 响应仍查 `model.http`，派发日志不承诺上游收件或采用。
- **同一份记忆可能派发多次** → 每次用自己的 `spanId`，用同一个 `recallId` 追源；以数值上限和来源去重控制日志量。
- **日志队列可能丢失或跨期清理** → 沿用 `diagnostics.loss` 和 30 日留存；缺少单条记录不是相反证据。用受控模型断言请求体与日志相符，测试仅用合成文本。

## Migration Plan

保留现有日志 schema 封套、路径和保留期限，停用新增生产点即可回退。新旧 JSONL 可共存；旧记录没有新增事件，不回填或推断。
