## Context

2026-11-24 的本地验收记录 `design/20261124/Writer-人工验收已知问题.md` 区分了两个失败位置：

- **方案没有承接。** Agent 看到了同一 Session 的上一份反派方案；`worker.ts`、`NovelTools` 却把最新一句单独交给 `story-assets.ts` 的分句／关键词判断。「嗯，就按这个来改」和「我允许你所有操作」在资产模型派发之前被拒绝。写章 `insert` 也只看当前原句，且有单个 `this.inserted` 限制，不能在同一 Run 先改中期目标章、再改后期目标章。日志中会话结束不等于这些内容实际写入。
- **正文落盘后本轮新资料无法同步。** 2026-11-24 的 Run `328308c8-bf87-4697-9a13-78e76bd6af1d` 在第 4、5 轮创建反派与伏笔，第 6、7、8 轮保存第 5、6、10 章及对应大纲。第 11 轮 `book_generate_assets` 返回 `invalid_options`。直接增补分支只接受 `create`，确认方案的资产校验也按登记的动作核对 `create`。当前完成检查主要核对资料存在及提交位置，因此即使新反派说明仍写「尚未出场」，进度也能达到 5/5。
- **另一层是 Messages 参数解析。** 《蝙蝠侠》第 9 轮和海贼王设定新书第 12 轮收到 HTTP 成功，消息结束后 `JSON.parse` 仍未得到合法工具参数；坏轮未执行工具，但整个 Run 结束。现有日志不能区分供应商分片与客户端拼接的责任。海贼王设定书用「继续」达到 10/10，只证明已落盘内容可续接，不证明首次运行自动恢复。
- **输入交互。** `src/Harness.tsx` 有表单和多行 `textarea`，发送按钮与提交函数各有检查，没有输入框的 Enter 发送；正文编辑器不是这次快捷键的作用范围。

## Goals / Non-Goals

**Goals:**

- 在一个会话内，让「先看方案 → 按这个来改」自然衔接，直接写作命令也不必先走提案；不让作者重复资料名、ID 或工具参数。
- 保留按版本取材、伏笔阶段隔离和 Markdown 原稿保护，支持同一 Run 内多个不同目标的小范围插入；只能根据实际提交确认资料、大纲和正文结果。
- 同一个主 Agent 根据已提交正文同步本次新建资料，并用当前资料、正文和大纲的有效提交核对关联增补的完成状态。
- 恢复特定的外层 Messages 工具参数语法失败一次，保留可追踪的尝试和提交边界。
- Enter 发送、Shift+Enter 换行，覆盖中文输入法、键盘重复、现有发送条件与按钮路径。

**Non-Goals:**

- 不增加子 Agent、小说阶段机、额外会话、审批弹窗或必须先登记的直接写作流程。不改变 200 轮上限、上下文压缩及整体输出预算。
- 不实现任意选段替换／删除、自动重写全章／全书、重排章节或宣称多文件提交是原子事务；不改原有整章重写授权。
- 不重试所有供应商异常，不切换模型、不修补 JSON、不推断提供方一定截断了输出。只复用既有公开模型接入和本地日志机制。

## Decisions

### 1. 让会话给出修改范围，工具核对范围，不再要求每条消息重述方案

继续由同一个主 Agent 理解作者、查阅现稿并决定工具。新增一个有界的会话方案记录，**仅在作者要求先看方案、Agent 回答了一个可执行方案时使用**；它是对可见回复的引用和数据，不是授权／写入，也不是每次创作的必经步骤。

- 复用 `RunContext.history`、`authorLine` 和 Session 日志，通过小说工具给本轮提案登记可选的结构化范围。记录与真实作品、Session、发起请求和本轮实际保存的可见方案回复绑定：操作类别、新主体／伏笔的目的与关联约束、拟修改的大纲位置及目标章／剧情阶段。模型可以选用真实章 ID，不要求新资产先有作者点名的 ID。使可见回复中的范围与记录来自同一份数据；未展示、失败或被新方案替代的草稿不能被选中。
- 本轮作者的直接执行指令仍走已有写作工具，**不先登记方案**。当确实指代上一份可核对方案时，以真实本轮作者消息将该范围当作本 Run 的已确认修改意图；「按这个来改」及在明确上下文下的「我允许你所有操作」只承接该方案，并服从本轮更窄的限制。当对象有歧义或作者仍只询问／明确禁止写时不写，不从模型参数、附件、其他 Session／作品或不相关的旧消息取得范围。只有存在实质歧义或必须变更已同意的范围时才回问，不引入常规二次确认。
- 在 Worker／`NovelTools` 共享这份范围给资产、正文与大纲入口：用可操作的目标、动作和真实当前约束替代 `authorized`、`passageTargetAllowed` 等对确认句逐项匹配动作／类别的路径。不要用「反派」「已有主体」「登场」是否逐字出现作为是否构成已确认范围的唯一开关；把关联数量、阶段和不能覆盖的约束显式校验。各专用模型请求只取得本轮作者要求、核定的方案摘要和局部资料，仍不继承完整对话，也不把模型给出的 `direction` 当权限。
- 核对方案依赖的现稿版本；若修改目标仍一致且锚点可安全重定位，可以按最新修订重新准备；已经发生实质冲突或需要扩大范围时把具体缺口交还主 Agent。原稿、引用、书界和版本检查是数据一致性，不引入账户权限、全局许可或 HITL。

**为什么不是继续加关键词或改为见到「允许」就全开：** 前者仍会丢失「这个」的所指，后者会把无关文件／旧稿混入。轻量方案记录只补齐确认所缺的引用，不决定 Agent 的工具顺序。

### 2. 跨章增补复用单处插入，按实际目标去重和验收

- 主 Agent 从已确认范围选择本次缺项，按需生成新反派／关联伏笔和针对各章的局部安排。每处正文仍调用现有锚点式 `insert`：当前修订、唯一原文位置、前后衔接、到本章允许披露的设定或线索。先写哪个合法目标由主 Agent 判断，不固定中期 → 后期的工具调用顺序；各章素材始终按故事发生位置裁决。
- 以具体修改操作身份做去重，区分章 ID、锚点和本次目的，替代「有任意一次插入就全 Run 拒绝」。不同合法目标可以独立提交；同一处重试不重复写，同一章若要另一处变更也需独立且唯一的合法锚点。按每处当前修订更新对应的大纲片段；同一 Run 的旧大纲版本不在多个提交之间重复使用。
- 优先保留被修改章锚点两侧、非目标章和无关资产的原字节；不因定位失败回落到整章重写。核对实际主体／伏笔、大纲和每个必要章节的提交回执及现稿后，才声称执行完方案。若只成功一部分，显示已提交与未完成项，保留成功部分；下一次接手先读现稿及回执，不重复生成已落盘资产／段落。计划回收与实际写出的回收分开。

**为什么不是批量重写章节或添加全书执行器：** 作者要的是分布式增补。现有单处锚点流程可逐处保护旧内容，也更容易对部分成功给出真实回执。

### 新建资料随已提交正文同步

- **授权来自执行范围和实际提交。** 在直接关联增补及同会话确认的执行中，复用 `book_generate_assets` 的 `update`。同一执行范围内创建成功的资料可按关联正文的实际提交同步剧情状态。用书、会话、执行范围、资料类型及稳定 ID 关联成功的创建回执与修订。后续同步还须核对作者最新限制、资料当前修订和对应章节提交。模型传来的资料 ID、`direction` 或剧情描述只用于定位。关联的旧主体和其他资料的更新按已有的明确授权校验。
- **依据已保存的事实和明确的计划。** 初次生成时，将尚待写出的情节放进计划。每个关联片段提交后，回执列出需要同步的资料和章节，主 Agent 可在有足够证据时调用资产工具。后端从本次关联的成功正文提交中选取当前版本和有界原文，核对章节、修订及唯一引用位置。主体同步只更新「已发生变化」与本次相关的「计划」。伏笔同步只更新与本次埋设、回收相关的说明，分别保留可见线索和回收内容。服务端按节合并，保留稳定设定、无关段落、标题、ID、结构化链接和锚点。新事实须有实际原文摘录支持。对照相应已保存章段逐条核对伏笔回收，角色本人登场只确认登场事实。证据只支持埋设或部分兑现时，记录已发生部分，并保留尚待实现的计划。大纲按已写安排对应各章。
- **完成以版本和覆盖范围计算。** 当关联片段提交时，将其纳入相关新建资料待核对的范围。复用版本化写入，并保存有界的同步回执，绑定资料最终修订、已覆盖的目标与对应正文修订。同步后若同一执行新增相关正文，新的提交进入待核对项。一次同步可覆盖多处已提交内容。重复请求只有在回执仍覆盖当前版本、目标和范围时才复用。后端验证证据、章节及修订、结构和回执覆盖，并在完成检查中读取实际落盘结果。回执中的状态必须符合引用的正文，实盘验收逐条核对；版本与引用校验提供可追溯性。
- **保留部分成功及续接路径。** 资料同步失败、缺少有效证据或发生版本冲突时，保留已提交的正文、大纲和资料，返回待核对目标与原因，结束时保持未完成。对能按现有规则唯一承接的未完成方案，用成功的创建、正文、大纲及同步回执恢复范围和进度，先核对当前版本，再执行缺项。对于缺少可承接范围或可靠回执的历史作品，由作者明确提出针对当前资料的修改请求。主 Agent 保有工具调度权。

### 3. 在外层请求边界识别坏 JSON，并有界重取本轮

- `parseMessages` 只在完整结束、仍得到不可解析工具参数、未返回任何可执行调用时给出可区分的内部失败类。保持批次严格：坏块及本来可解析的同批块都不能执行；对完整但 Schema 不合法的参数仍按现有工具反馈处理。断流、触限、鉴权、取消和其他 `malformed_stream` 不误入这一分支，独立的资产／正文生成重试不被叠加。
- 主循环在尚未把该批交给 Pi 工具执行器的请求边界，用最后一份合法请求投影重取同一逻辑轮一次；不把坏回复、无效工具 ID 或其暂态文本写进模型历史，不重放已结算的动作。清掉失败尝试的临时流式显示，不撤销以前的会话消息或文件。重取使用新请求 span、同一 Run／轮次，真实工具回传在诊断中可与重取请求区分，不重复生成业务回执。
- 重取成功按正常路径校验和执行，取消则停止；仍无法解析时返回具体失败、已保留进度、同书续接提示和可定位的诊断编号，不再循环。已有独立的超时、输出预算、取消和往返计数保持原有含义。
- 后端白名单仅增加必要结构：结束标志、归一化的结束类型、发生问题的块索引、块／分片数量、可用的已缓冲 UTF-8 字节数、解析分类、尝试序号和原／重取 span 关联。限定条数并计数遗漏，不记录原参数、JSON 异常里的内容片段、正文、作者原话或密钥。修改范围诊断只记来源类型、目标数量、失败类别及脱敏关联，继续使用实际提交事件作为写入证据。

**为什么不是修尾括号、部分执行或重开整书：** 无法从损坏参数确认原意，同批部分执行会留下难以安全续接的状态；重开整书会重做成功提交。单轮重取只覆盖当前已证实没有工具执行的边界。

### 4. 键盘与按钮共用一个表单提交入口

只处理 Harness 消息框有焦点时不带修饰键的 Enter，通过现有表单提交入口发送。Shift+Enter 留给 `textarea` 的原生插入行为（光标位置、多行和选区照常），不拦 Ctrl／Alt／Meta 等其他组合。发送的可用性判断集中供表单和按钮复用，包括空白、无有效模型、当前会话缺失／工作区不可用、正在运行、正在提交；首个提交开始即防重复，成功才按既有行为清空文本和附件，失败保留供修正。

检查键盘事件及组合输入状态，覆盖 Windows 中文输入法选字/上屏的 Enter；组合输入确认及重复键按不启动 Run，不截断候选操作。发送／停止按钮仍可用，键盘发送不停止运行中的任务，不在全局或 Markdown 编辑器接管 Enter；在输入框附近提供简短快捷键提示。

**为什么不是 `keydown` 直接发 IPC：** 保持一次发送的会话、模型、思考档位、选中章和附件一致，避免绕过表单校验、双发或误清内容。

## Risks / Trade-offs

- [确认指向过期或未展示的方案] → 只承接同书同 Session 可定位的有效方案，明确本轮的缩小／否定约束；读取版本时按现稿核对，不静默扩大范围。
- [多处写入中途失败] → 不承诺原子回滚；每处保有版本与实际回执，报告剩余范围，复验防旧锚点、重复提示和误改他章。
- [把计划或登场当成伏笔回收，或遇到外部修订] → 逐条按当前正文取证，并在写入前复核资料及来源修订。保留已保存结果和待同步项，诊断仅记录类型、计数、拒绝原因和脱敏标识。
- [重取增加延迟、费用或重复可见文本] → 仅特定失败且未执行工具时一次；区分临时流和已追加消息，日志核对不同 span 与唯一的实际工具执行。
- [输入法在合成结束边界误发送] → 受控组合输入用例外，实际 Windows 中文输入法手验一次；完整覆盖 Shift+Enter 和按钮仍可用。

## Migration Plan

会话日志增加可选、受界的方案元数据和同步回执，旧会话和旧稿按原格式读取，无项目数据迁移。旧版本仅有纯文本的历史提案不会被静默当成执行范围；可在同一会话按新行为重新提出方案、再确认，或直接明确下达修改要求，无须重建作品。若需回退，既有 Markdown 与旧会话记录不改写；测试以独立的隔离书库确认读写和续接。桌面验收默认在后台隐藏，不打扰作者正在用的窗口。

## Open Questions

Messages 错误是供应商输出还是客户端拼接造成，当前证据不足；用新增诊断继续定位。该不确定性不阻碍严格拒绝坏批次、对本轮做一次有限重取。
